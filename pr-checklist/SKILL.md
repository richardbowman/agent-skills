# PR Checklist — Definition of Done

A feature is NOT done until every item below passes. Do not open a PR, push to
main, or mark a Linear issue In Review until this checklist is complete.

## Step 0 — Load Per-Repo Guidelines

**Before running any checklist step**, check whether `.claude/pr-guidelines.md`
exists in the project root:

```bash
ls .claude/pr-guidelines.md
```

**If the file exists:** read it and let it override or extend every step below.
The guidelines file is the authoritative source for this repo's definition of
done. Any command, viewport, coverage threshold, or process it specifies takes
precedence over the defaults in this skill.

**If the file does not exist:** offer to create it before proceeding:

> "This project doesn't have a `.claude/pr-guidelines.md` yet. That file lets
> you customize the PR checklist per repo — commands, viewports to test,
> screenshot tooling, docs location, coverage requirements, etc.
>
> Want me to set it up now? I'll ask a few questions about this project and
> generate a tailored file. (You can also say 'skip' to run the default
> checklist this time.)"

If the user says yes, run the **Guidelines Setup Wizard** below. If they say
skip, continue with the defaults in Steps 1-6.

## Guidelines Setup Wizard

Ask the following questions, then write `.claude/pr-guidelines.md`. Commit it
so all contributors and future Claude sessions inherit the config.

**Questions to ask:**

1. **Package manager:** pnpm / npm / yarn / bun?
2. **TypeScript:** Which tsconfig is used for type-checking? (e.g.
   `tsconfig.build.json`, `tsconfig.json`, or none)
3. **Unit tests:** What command runs them? Any minimum coverage threshold?
4. **E2E tests:** What command runs them? (e.g. `pnpm test:e2e`) Any known
   setup steps (env file, dev server, seed data)?
5. **UI surfaces:** Does this app have a browser UI? If yes:
   - Which desktop viewport(s) to check? (default: 1280x800)
   - Which mobile viewport(s) to check? (default: 390x844, iPhone 14)
   - Any tablet breakpoints worth checking?
   - Does the app have any special dark-mode, RTL, or accessibility modes that
     need visual checks?
6. **Screenshot tooling:** Is there a script to regenerate screenshots?
   (e.g. `pnpm docs:screenshots`) Where are they committed?
7. **Docs location:** Where do user-facing docs live? (e.g. `docs/`, `content/`,
   `README.md`)
8. **Linear / issue tracker:** Should the checklist remind to move issues to
   In Review?
9. **Anything else:** Any project-specific gates (e.g. bundle size check,
   migration safety review, accessibility audit)?

Write the output as a Markdown file using the template below. Fill in every
section the user answered; omit sections that don't apply.

### Template for `.claude/pr-guidelines.md`

```markdown
# PR Guidelines — <Project Name>

Generated by the pr-checklist skill. Edit freely.

## Commands

| Task | Command |
|---|---|
| Type-check | `<tsc command>` |
| Unit tests | `<test command>` |
| E2E tests | `<e2e command>` |
| Screenshots | `<screenshot command or "none">` |

## Coverage Requirements

- Unit test minimum: <threshold or "none specified">
- E2E: every new user-facing flow must have a test

## Visual Verification

Whenever any UI is touched, manually verify at these viewports before opening
the PR:

- **Desktop:** <e.g. 1280x800>
- **Mobile:** <e.g. 390x844 (iPhone 14)>
- <any additional viewports>

For each viewport, confirm:
- [ ] Layout is not broken (no overflow, no collapsed sections)
- [ ] Interactive elements are reachable and usable
- [ ] No visual regressions from the diff
- <any project-specific items, e.g. dark mode, RTL>

## Docs Location

User-facing docs live in `<path>`. Review and update any page related to the
changed feature.

## Issue Tracker

Move the Linear issue to **In Review** before opening the PR.

## Project-Specific Gates

<list any extra gates, or delete this section>
```

## Step 1 — Types

Run the TypeScript compiler and fix all errors before anything else. Use the
command from `.claude/pr-guidelines.md` if present; otherwise:

```bash
pnpm tsc --noEmit --project tsconfig.build.json
```

## Step 2 — Unit Tests

Run the command from `.claude/pr-guidelines.md` if present; otherwise:

```bash
pnpm test
```

**Requirements:**
- All existing tests pass — do not skip or delete tests to force a green suite
- New tests written for every new function, API route, and component
- Minimum coverage: happy path + at least one error/edge case per unit
- Honor any coverage threshold specified in the guidelines file
- Use the project's established mock patterns

## Step 3 — E2E Tests

Run the command from `.claude/pr-guidelines.md` if present; otherwise:

```bash
pnpm test:e2e   # use the e2e-local skill to set up environment first
```

**Requirements:**
- Any new or changed user-facing flow has a corresponding E2E test
- All existing E2E tests still pass

**If the test command crashes before running any tests** (e.g. "Vitest cannot
be imported in CommonJS", "command not found", process exits before reporter
output): this is a **tooling bug, not a test failure**. Stop and fix the
tooling before treating any work as done.

## Step 4 — Visual Verification

**Skip this step entirely if no UI files were touched in this branch.**

If the guidelines file defines viewports, use those. Default viewports when no
guidelines file exists:

- **Desktop:** 1280x800
- **Mobile:** 390x844 (iPhone 14)

For each viewport, manually verify (or use Playwright/screenshot tooling if
available):

- [ ] Layout is not broken — no unexpected overflow, collapsed sections, or
  misaligned elements
- [ ] All interactive elements are reachable and visually correct
- [ ] No regressions visible in the changed area compared to the design or
  pre-change state
- [ ] Any project-specific modes from the guidelines (dark mode, RTL, etc.)
  also checked

If a visual regression is found, fix it before proceeding. Do not open a PR
with a known visual bug and plan to fix it "later."

## Step 5 — Docs Review

Docs location comes from `.claude/pr-guidelines.md` if present; otherwise
check `docs/` or the project root.

- Read every doc page related to the changed feature
- Update copy if any user-facing label, flow, or behavior changed
- Add a new doc page if the feature is entirely new to users

## Step 6 — Screenshots

If the guidelines file specifies a screenshot command, or the project has a
`pnpm docs:screenshots` script:

```bash
<screenshot command>
```

- Run after any UI change
- Commit updated screenshots alongside the code change

## Step 7 — Final PR Checklist

Build the final checklist from the guidelines file if present; otherwise use
these defaults. Present it to the user as a completed checklist with pass/fail
status for each item:

- [ ] TypeScript: `tsc --noEmit` clean
- [ ] Unit tests: passing + new tests written
- [ ] E2E tests: passing + new/updated tests written
- [ ] Visual verification: desktop and mobile viewports checked (if UI touched)
- [ ] Docs: reviewed and updated for any changed user-facing behavior
- [ ] Screenshots: regenerated and committed (if project has screenshot tooling)
- [ ] Linear issue: moved to **In Review**
- [ ] PR title: concise, describes the change
- [ ] PR description: explains *why* the change was made, not just *what*

## When to Invoke This Skill

Invoke this skill proactively at the end of any development task — before
declaring it done, before asking the user to review, and before opening a PR.
The user should never have to ask "did you run the tests?" — that should always
already be done.

## Making This Structural (Autonomous Work)

"Invoke proactively" is voluntary and fails under momentum. If you are doing
autonomous work on a project — especially multi-step builds where you will push
multiple times — install the enforcement hook **before starting**, not after
something breaks.

Check whether `.claude/settings.json` exists in the project root. If it
doesn't, create it with this hook:

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "if": "Bash(git push*)",
            "command": "jq -r 'if (.tool_input.command | test(\"git push\")) then {\"hookSpecificOutput\":{\"hookEventName\":\"PostToolUse\",\"additionalContext\":\"QUALITY GATE: You just pushed to git. Before declaring this work done you MUST run the pr-checklist skill (or check .claude/pr-guidelines.md for this repo's requirements). Do not tell the user the work is done until the full checklist passes.\"}} | tojson else empty end'",
            "timeout": 5
          }
        ]
      }
    ]
  }
}
```

This injects a blocking reminder into context after every `git push`, making
the checklist structural rather than voluntary. Commit `.claude/settings.json`
so it applies to the whole project, not just one session.
