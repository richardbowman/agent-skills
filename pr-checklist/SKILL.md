# PR Checklist — Definition of Done

## Harness portability

Use the active harness's shell, file, test, browser, and image-inspection capabilities. Look for `.agents/pr-guidelines.md` and `.claude/pr-guidelines.md`; if both exist, merge compatible requirements and stop on conflicts. Harness hook formats are optional enforcement adapters—the checklist itself remains authoritative in Claude Code and Codex.

A feature is NOT done until every item below passes. Do not open a PR, push to
main, or mark a Linear issue In Review until this checklist is complete. Once
the checks finish, publish their QA summary in the GitHub PR as described in
Step 7; the detailed report (a Compass Doc on Compass projects, a vault note otherwise) remains the durable evidence record.

## Step 0 — Load Per-Repo Guidelines

**Before running any checklist step**, resolve the repository guidance file:

```bash
for f in .agents/pr-guidelines.md .claude/pr-guidelines.md; do test -f "$f" && echo "$f"; done
```

**If the file exists:** read it and let it override or extend every step below.
The guidelines file is the authoritative source for this repo's definition of
done. Any command, viewport, coverage threshold, or process it specifies takes
precedence over the defaults in this skill.

**If neither file exists:** offer to create the harness-native file before proceeding (`.agents/pr-guidelines.md` for Codex, `.claude/pr-guidelines.md` for Claude Code):

> "This project doesn't have a harness PR-guidelines file yet. That file lets
> you customize the PR checklist per repo — commands, viewports to test,
> screenshot tooling, docs location, coverage requirements, etc.
>
> Want me to set it up now? I'll ask a few questions about this project and
> generate a tailored file. (You can also say 'skip' to run the default
> checklist this time.)"

If the user says yes, run the **Guidelines Setup Wizard** below. If they say
skip, continue with the defaults in Steps 1-6.

## Guidelines Setup Wizard

Ask the following questions, then write the harness-native guidelines file. Commit it
so all contributors and future assistant sessions inherit the config.

**Questions to ask:**

1. **Package manager:** pnpm / npm / yarn / bun?
2. **TypeScript:** Which tsconfig is used for type-checking? (e.g.
   `tsconfig.build.json`, `tsconfig.json`, or none)
3. **Unit tests:** What command runs them? Any minimum coverage threshold?
4. **E2E tests:** What command runs them? (e.g. `pnpm test:e2e`) Any known
   setup steps (env file, dev server, seed data)?
5. **UI surfaces:** Does this app have a browser UI? If yes:
   - Which desktop viewport(s) to check? (default: 1280x800)
   - Which mobile viewport(s) to check? (default: 390x844, iPhone 14)
   - Any tablet breakpoints worth checking?
   - Does the app have any special dark-mode, RTL, or accessibility modes that
     need visual checks?
6. **Screenshot tooling:** Is there a script to regenerate screenshots?
   (e.g. `pnpm docs:screenshots`) Where are they committed?
7. **Docs location:** Where do user-facing docs live? (e.g. `docs/`, `content/`,
   `README.md`)
8. **Linear / issue tracker:** Should the checklist remind to move issues to
   In Review?
9. **Anything else:** Any project-specific gates (e.g. bundle size check,
   migration safety review, accessibility audit)?

Write the output as a Markdown file using the template below. Fill in every
section the user answered; omit sections that don't apply.

### Template for the harness-native PR guidelines

```markdown

Generated by the pr-checklist skill. Edit freely.

| Unit tests | `<test command>` |
| E2E tests | `<e2e command>` |

- E2E: every new user-facing flow must have a test

For each viewport, confirm:
- [ ] Layout is not broken (no overflow, no collapsed sections)
- [ ] Interactive elements are reachable and usable
- [ ] No visual regressions from the diff
- <any project-specific items, e.g. dark mode, RTL>
```

## Step 1 — Types

Run the TypeScript compiler and fix all errors before anything else. Use the
command from `.claude/pr-guidelines.md` if present; otherwise:

```bash
pnpm tsc --noEmit --project tsconfig.build.json
```

## Step 2 — Unit Tests

Run the command from `.claude/pr-guidelines.md` if present; otherwise:

```bash
pnpm test
```

**Requirements:**
- All existing tests pass — do not skip or delete tests to force a green suite
- New tests written for every new function, API route, and component
- Minimum coverage: happy path + at least one error/edge case per unit
- Honor any coverage threshold specified in the guidelines file
- Use the project's established mock patterns

## Step 3 — E2E Tests

Run the command from `.claude/pr-guidelines.md` if present; otherwise:

```bash
pnpm test:e2e   # use the e2e-local skill to set up environment first
```

**Requirements:**
- Any new or changed user-facing flow has a corresponding E2E test
- All existing E2E tests still pass

**If the test command crashes before running any tests** (e.g. "Vitest cannot
be imported in CommonJS", "command not found", process exits before reporter
output): this is a **tooling bug, not a test failure**. Stop and fix the
tooling before treating any work as done.

## Step 4 — Visual Verification

**Skip this step entirely if no UI files were touched in this branch.**

If the guidelines file defines viewports, use those. Default viewports when no
guidelines file exists:

- **Desktop:** 1280x800
- **Mobile:** 390x844 (iPhone 14)

For each viewport, manually verify (or use Playwright/screenshot tooling if
available):

- [ ] Layout is not broken — no unexpected overflow, collapsed sections, or
  misaligned elements
- [ ] All interactive elements are reachable and visually correct
- [ ] No regressions visible in the changed area compared to the design or
  pre-change state
- [ ] Any project-specific modes from the guidelines (dark mode, RTL, etc.)
  also checked

If a visual regression is found, fix it before proceeding. Do not open a PR
with a known visual bug and plan to fix it "later."

**Write a QA report — do not skip this even if you're about to summarize in
chat.** Chat summaries are invisible to the user when this skill runs inside
a background subagent; a written report is the only durable record.

**Where the report goes depends on the project. Decide first:**
the project uses Compass if `pm-config.md` (repo root, or `Products/<Project>/pm-config.md`
in the vault) has a `## Provider Connections → Compass` section. If it does, **Compass is the
primary record** (path A) and the vault is a fallback. If not, use the vault only (path B).

### Path A — Compass project (primary)

1. **Resolve the workspace** from that section (`Org slug`, `Workspace slug`, `Workspace ID`).
   Geode sessions already have the native `mcp__compass__*` tools authenticated; elsewhere use
   the credential the section names.
2. **Find or create the Compass Task this PR delivers** (`list_tasks` for the branch/PR/topic;
   else `create_task`, status `IN_REVIEW`, with the PR link once it exists). Link it to its
   Solution or Roadmap Item with `link_task` when one fits; if none fits, say so in the report
   rather than inventing one. Every PR on a Compass project needs a Task: the gate checks for it.
3. **Write the QA report as a Compass Doc**, kind `QA_REPORT`:
   ```
   write_doc(workspaceId,
     path: "QA Reports/<YYYY-MM-DD> <feature or PR title>",
     kind: "QA_REPORT",
     content: <markdown: heading "## QA Report — <HH:MM>"; per viewport/mode pass/fail against
               the four bullets above; commands run with their REAL pass/fail counts and the
               machine they ran on; screenshots taken; a "NOT VERIFIED" list; PR and preview
               links; if screenshots are in the vault, their vault-relative paths>)
   ```
   Record only OBSERVED output. Mark anything unverified as NOT VERIFIED. Get the doc's id and
   url from `list_docs(kind: "QA_REPORT")`.
4. **Link it to the Task:** `link_task(taskId, linkedType: "DOC", linkedId: docId)`, and post
   `add_comment(targetType: "TASK", targetId: taskId, authorName: "Claude Code", body: "QA
   Report: <doc url> — PASS|FAIL")`. If a Solution is known, also comment on it
   (`add_solution_comment`).
5. **Screenshots** stay in the vault (Compass Docs have no image hosting):
   `Attachments/QA/<Project>/<YYYY-MM-DD>-<slug>/`. Embed real images in a short pointer note
   `Products/<Project>/Runs/<slug>-<YYYY-MM-DD>-<topic>.md` that links to the Compass doc,
   or just reference the vault paths from the Compass doc. "Verified visually" with no attached
   image does not satisfy this step. Link any vault file you create from today's
   `Daily/YYYY-MM-DD.md` under `## Claude Sessions`.
6. **Write the gate receipt** (only when the checks actually passed). Directory
   `~/.claude/qa-gates/` (create it if missing), file name = branch with each `/` and space
   replaced by `__`, plus `.gate`; one line:
   ```
   QA-GATE: PASS branch=<branch> task=TASK-<n> report=<Compass doc URL>
   ```
   The PR-create hook requires `task=` and `report=`, the right branch, and a file touched in the
   last 24h.
7. **Compass unavailable?** Only if the Compass tools return real errors (not merely slow):
   write the report to the vault run note `Products/<Project>/Runs/<slug>-<YYYY-MM-DD>-<topic>.md`
   with a `## QA Report — <HH:MM>` section, then add these two lines to it:
   ```
   QA-GATE: PASS branch=<branch>
   COMPASS-UNAVAILABLE: <the actual error text>
   ```
   and back-fill the Compass Doc and Task link once Compass returns (then write the receipt).

### Path B — project without Compass (vault only)

1. Find or create today's per-run vault note:
   `Products/<Project>/Runs/<project-slug>-<YYYY-MM-DD>-*.md` (vault-relative; project name
   from the repo directory/`package.json`, capitalized). Append to today's note if one exists
   (most recently modified if several); otherwise create `...-<YYYY-MM-DD>-qa.md`.
2. Append a `## QA Report — <HH:MM>` section listing, per viewport/mode checked: pass/fail
   against the four bullets above, and what was actually different if something failed and got
   fixed.
3. **Embed real screenshots, not descriptions.** Save each under
   `Attachments/QA/<Project>/<YYYY-MM-DD>-<slug>/` and embed with
   `![[Attachments/QA/<Project>/.../file.png]]`.
4. Add the line `QA-GATE: PASS branch=<branch>` to that note once everything passed, and link it
   from today's Daily note.

### Both paths

- Chat summaries are invisible when this skill runs inside a background subagent; the written
  report is the only durable record. Publish repository-owned documentation through the
  repository's normal Git commit, push, and PR workflow, not through the vault.
- When you report completion (to the user or to whoever spawned you), state the Compass Doc URL
  and Task id (Path A) or the exact vault path (Path B or fallback). That is the proof the
  verification happened.

## Step 5 — Docs Review

Docs location comes from `.claude/pr-guidelines.md` if present; otherwise
check `docs/` or the project root.

- Read every doc page related to the changed feature
- Update copy if any user-facing label, flow, or behavior changed
- Add a new doc page if the feature is entirely new to users

## Step 6 — Screenshots

If the guidelines file specifies a screenshot command, or the project has a
`pnpm docs:screenshots` script:

```bash
<screenshot command>
```

- Run after any UI change
- Commit updated screenshots alongside the code change

## Step 7 — Publish the QA Report to the GitHub PR

Build a concise Markdown summary from the checks actually run. Do not claim a
check passed without its command output or other direct evidence. Include:

- overall status: pass or fail
- type-check, unit-test, and E2E commands with their results
- visual viewports/modes checked, or `Not applicable — no UI changes`
- docs and screenshot results
- known gaps, skipped checks, or environment limitations
- the exact vault path of the detailed QA report, when one was written
- the Compass doc URL and what it's linked to, when Step 4 item 6 applied

Wrap the summary in stable markers so rerunning the checklist replaces the
existing report instead of appending duplicates:

```markdown
<!-- qa-report:start -->
## QA Report

**Status:** PASS | FAIL

| Check | Result | Evidence |
|---|---|---|
| Type-check | PASS | `<command>` — <result> |
| Unit tests | PASS | `<command>` — <count/result> |
| E2E tests | PASS | `<command>` — <count/result> |
| Visual verification | N/A | No UI changes |
| Docs/screenshots | PASS | <what was reviewed or regenerated> |

**Known gaps:** None.

**Detailed evidence:** `<compass-doc-url, or vault path when Compass was unavailable or the project has none>`
**Compass doc:** `<url, or "N/A — project not Compass-managed">`
<!-- qa-report:end -->
```

Resolve whether the current branch already has a PR with `gh pr view`. Then:

- **PR exists:** read its current body, replace the content between the QA
  markers if present (otherwise append the marked block), and update the same
  PR with `gh pr edit --body-file <file>`. Preserve every other part of the PR
  body verbatim. Read the PR body back afterward and confirm the marked report
  is present.
- **No PR exists yet:** retain the complete marked block for the PR-creation
  step. The `create-pr` skill must include it in the initial PR body and verify
  it after creation. Do not open a PR merely because this checklist ran unless
  opening one is already authorized by the user's request.

If GitHub authentication, permissions, or network access prevents publication,
report the exact failure and return the ready-to-paste marked block. Do not
describe the GitHub QA report as published until the read-back verification
succeeds.

## Step 8 — Final PR Checklist

Build the final checklist from the guidelines file if present; otherwise use
these defaults. Present it to the user as a completed checklist with pass/fail
status for each item:

- [ ] TypeScript: `tsc --noEmit` clean
- [ ] Unit tests: passing + new tests written
- [ ] E2E tests: passing + new/updated tests written
- [ ] Visual verification: desktop and mobile viewports checked (if UI touched)
- [ ] QA report written (if any tests were run or visual verification was performed):
      Compass projects: Compass Doc (kind QA_REPORT) linked to the Compass Task, gate receipt
      written, state doc URL + task id; vault fallback only if Compass errored
      (`COMPASS-UNAVAILABLE` line). Other projects: vault run note with embedded screenshots,
      state the path
- [ ] GitHub PR body contains the current marked QA report, or the marked block
      is ready for an authorized PR-creation step
- [ ] Docs: reviewed and updated for any changed user-facing behavior
- [ ] Screenshots: regenerated and committed (if project has screenshot tooling)
- [ ] Linear issue: moved to **In Review**
- [ ] PR title: concise, describes the change
- [ ] PR description: explains *why* the change was made, not just *what*

## When to Invoke This Skill

Invoke this skill proactively at the end of any development task — before
declaring it done, before asking the user to review, and before opening a PR.
The user should never have to ask "did you run the tests?" — that should always
already be done.

## Making This Structural (Autonomous Work)

"Invoke proactively" is voluntary and fails under momentum. If you are doing
autonomous work on a project — especially multi-step builds where you will push
multiple times — install the enforcement hook **before starting**, not after
something breaks.

Claude Code adapter: check whether `.claude/settings.json` exists in the project root. If it
doesn't, create it with this hook. Codex does not use this hook schema; keep the
gate in `AGENTS.md` and the skill checklist instead of writing an incompatible hook.

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "if": "Bash(git push*)",
            "command": "jq -r 'if (.tool_input.command | test(\"git push\")) then {\"hookSpecificOutput\":{\"hookEventName\":\"PostToolUse\",\"additionalContext\":\"QUALITY GATE: You just pushed to git. Before declaring this work done you MUST run the pr-checklist skill (or check .claude/pr-guidelines.md for this repo's requirements). Do not tell the user the work is done until the full checklist passes.\"}} | tojson else empty end'",
            "timeout": 5
          }
        ]
      }
    ]
  }
}
```

This injects a blocking reminder into context after every `git push`, making
the checklist structural rather than voluntary. Commit `.claude/settings.json`
so it applies to the whole project, not just one session.
